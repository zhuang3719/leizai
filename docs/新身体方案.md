## 二、核心机制：内存态分身（in-memory shadow）

这是整个方案的心脏，直接解决"改错起不来"。

### 2.1 工作流（5 步）
```
① 进内存 —— 启动时把当前 data/ + src/ 快照为内存态，进程绑定快照，不直读硬盘实体
② 内存里改 —— 自我修改在内存快照上做，任意折腾，硬盘原文件不动
③ 内存里验 —— 在内存态跑验证：node --check 语法 / 模块require / 完整自测
④ 确认才落盘 —— 验证通过才写回硬盘 data/ + src/（落盘前再 node --check 兜底）
⑤ 永久可回退 —— 每次落盘前把上一版存入 versions/ 版本链，可一键倒回任意历史版本
```

### 2.2 三层保险
- **第一层 · 改动前快照**：改任何文件前，先备份当前版本为 `.bak`。
- **第二层 · 落盘前验证**：`node --check` 通过 + 模块能 require 才允许写回；验证不过 → 丢弃改动，身体保持原样。
- **第三层 · 启动时自动回滚**：server.js 启动最前自检，加载核心模块抛异常 → 检测 `.bak`/版本链，自动回退上一好版本再继续启动。

### 2.3 "改错"边界定义
指一切**非故意、导致身体不可用或数据受损**的意外：
- 语法/逻辑错（前端/后端/核心改动后崩溃）→ 三层保险兜住。
- 数据错（误删/覆盖记忆、技能、会话、归档）→ 数据层写前快照 + 索引一致性校验 + 可回滚。
- 运行环境错（Python/Node 环境、网络、依赖）→ 健康检查 + 依赖自检 + 降级不中断。
- 外部影响错（改动波及并行分身/子智能体）→ 隔离验证，只影响自己。

**故意破坏性命令**（如 rm -rf 删数据）不在"改错"范畴，但单独用"关键目录只读保护"防住。
