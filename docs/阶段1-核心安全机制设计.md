# 阶段1 · 核心安全机制设计（自修改永不"改到无法启动"）

> 目标：新身体（<REPO_ROOT>）无论怎么自我修改前端/后端/核心，都不会因为改错而无法启动。
> 机制：**影子写入（shadow commit）+ 启动自检回滚（boot-guard）+ 版本链（version chain）** 三层。
> 说明：本文件是"给雷仔过目的设计稿"，确认后才落地到代码。

---

## 一、关键认知：引擎改动的本质

雷仔改自己 = 调用 `write_file` / `edit_file` 工具改写 `src/*.js` 等源码文件。
`node src/server.js` 启动时就加载这些源码。**旧身体的问题**：改源码是"就地覆盖"，改错（语法错/加载错）→ 下次启动直接崩 → 无法启动。

新身体要做的，就是把"就地覆盖"改成"**影子写入 + 验证 + 版本链回退**"，并在启动前加一道"**自动回滚守卫**"。

---

## 二、三层机制

### 第 1 层：影子写入（shadow commit，改错不外泄）

改造 `src/tools.js` 的 `write_file`/`edit_file`：当目标文件**命中"自我修改范畴"**（`src/` 目录下的源码、`data/prompts/` 的人格/规则、`config.json`）时，不直接落盘，而是走影子写入：

```
write_file(目标, 内容)
  → ① 备份：把"目标当前版本"快照到 versions/链（带时间戳+哈希）
  → ② 影子写入：先把新内容写到内存/临时文件（shadow），不碰实体
  → ③ 验证：对 shadow 跑语法/加载校验（.js→node --check；.json→JSON.parse；.md 免验）
  → ④ 验证通过 → 才把 shadow 落盘（writeFileSync 到实体）
  → ⑤ 验证失败 → 丢弃 shadow，实体保持原样，抛出拦截错误（不给写坏版本机会）
```

**核心效果**：坏版本在 ③ 就被拦下，根本写不进实体 → 实体永远是"可启动的好版本"。

### 第 2 层：启动自检回滚（boot-guard，兜底三保险）

改造 `src/server.js`，在 `listen` 前加一段自检：

```
bootGuard()
  → ① 扫描 src/ 全部 .js，逐个 node --check（语法）
  → ② require 一遍核心模块（config/runtime/...）确认能加载
  → ③ 任何一个失败 → 从 versions/ 链里找"最近一个好版本"，自动回退覆盖实体
  → ④ 回退成功 → 用回退后的版本重新 check/require，通过才继续 listen
  → ⑤ 全部通过 → 正常启动；若无法自愈 → 明确报错 + 给出指到最近好备份的路径（仍保底可手动还原）
```

**核心效果**：万一坏版本绕过第1层写进实体，启动时也会被 ①② 发现，自动倒带到版本链里最近的好版本 → **永远能起来**。

### 第 3 层：版本链（version chain，永久可回退）

- `<REPO_ROOT>\data\versions\` 目录，每次影子写入前，把"当前实体版本"存为 `versions/<文件名>-<时间戳>.bak`（含哈希）。
- 版本链只增不减（保留最近 N 个，如 20 个），供启动自检回退 + 手动一键回退任意历史版本。
- 关键目录（`data/`、`config.json`）另加"只读保护"：`write_file`/`edit_file` 对"关键只读目录"直接拒绝（防故意破坏性命令），但 `src/`、`data/prompts/` 这类"自我修改范畴"放行（走影子写入）。

---

## 三、"自我修改范畴" vs "关键只读目录" 的边界

| 路径 | 处理 |
|------|------|
| `src/*.js`（引擎源码） | ✅ 允许改，走**影子写入+验证**（放心改核心） |
| `data/prompts/`（人格/规则 system.md, harness.md） | ⚠️ 允许改，走影子写入（但要触发前缀护栏） |
| `config.json` | ⚠️ 允许改，走影子写入中 JSON 校验 |
| `workspace/`（我的工作区） | ✅ 正常写（不做影子，轻量不拦截） |
| `data/`（记忆/技能/会话/归档/进化） | ⛔ **只读保护**（防误删/破坏；但 memory.save 等内部接口仍可用） |
| `src/plugins/`（插件） | ⚠️ 允许改，走影子写入（避免改坏插件） |

> 说明：`data/` 记忆/技能/会话的"增删"仍走 `memory.save`/`save_skill` 等内部接口（那些是正常业务），**只读保护拦截的是"用 write_file 直接改写 data/ 关键文件"这种绕过业务接口的破坏性路径**。这样既防"故意 rm"，又不影响正常记忆/技能沉淀。

## 五、验收方式（模拟"改错"，反复验证永不无法启动）

1. **语法错**：故意用 shadow 写入一个语法错误的 `src/runtime.js` → 预期：第1层拦截，实体不变，引擎还能正常启动。
2. **逻辑错（绕过验证）**：强制写坏版本进实体 → 预期：第2层 boot-guard 启动时发现，自动回退到最近好版本，引擎仍能启动。
3. **数据破坏**：用 write_file 写 `data/memory/xxx.md` → 预期：只读保护拒绝，数据完好。
4. **JSON 错**：故意写坏 `config.json` → 预期：影子写入中 JSON 校验拦截，实体 config 完好。
5. **回退**：制造一次成功版本切换后，用版本链一键回退到上一个版本 → 预期：功能恢复。

> 验收全在"内存态/shadow"层面进行 + 启动验证，不破坏实体，不干扰旧身体（3457）与当前对话。

## 六、风险与边界

- **资源开销**：影子写入会多做一次备份+校验，但对"自我修改"这种低频操作可忽略；普通文件读写（workspace/业务）不受影响。
- **误判风险**：路径判定若误把"业务写"当作"自我修改"会拖慢；故在 `src/` `data/prompts/` 等明确范畴才启用影子，其余正常。
- **回退过度**：版本链只保留最近 N 个，避免无限膨胀；回退阈值可配。
- **与旧身体隔离**：所有改动落在 <REPO_ROOT>，旧身体（<LEGACY_ROOT>）代码完全不动，不受影响。
